# Python Software Factory — Agent Operating Manual

Polylith monorepo. Brick counts are derived from `BRICKS_INDEX.yaml`. Every brick = full MCP interface. Agents interact through MCP, never direct imports.

## NORTH STAR

The vision every session and sub-agent optimizes toward. When a decision is ambiguous, these win.

1. **Emergent best practices.** Use the current, proven way — not yesterday's habit. Check what the framework/SDK ships today before hand-rolling.
2. **Engineering excellence.** No bandaids, no shims, no "temporary" hacks. Elegant and simple over clever. Prefer framework primitives over bespoke code. Polymorphic where possible. Avoid both under- and over-engineering — solve the actual problem cleanly.
3. **Recursively learning system.** the control-plane runtime is a self-contained loop: it acts, observes outcomes, scores them, and improves itself the next cycle. Every feature should feed the loop, not dead-end.
4. **Game theory · RL · blockchain are first-class.** Games model strategic/adversarial dynamics; Reinforcement Learning drives system evolution; blockchain provides the trust/economy/provenance layer. Reach for them when a problem fits — they are core substrate, not bolt-ons.
5. **UX is paramount — the assistant drives everything.** The user should be able to do anything in the app *through* the assistant, and the assistant has full control of the app. Theme: minimal, clean, elegant, animation-forward.

## AGENTIC CONTROL PLANE — NORMATIVE

> Freeze the handshake, not the intelligence.
>
> Write only enough code to define safe handoffs, preserve evidence, and execute repeatable operations. Let agents perform work that requires intelligence: research, interpretation, planning, and adaptation.
>
> Agents decide and compose; bricks execute and guarantee; Evals challenge; Workflow remembers.

This file is the single normative authority for the control-plane split. Secondary docs describe current implementation and link here; they do not redefine ownership.

- **Agent brick — intelligent runtime.** Owns the runtime and persona registry, skills, model/tool scoping, structured outputs, native LangChain/LangGraph agent, middleware, checkpoint, and multi-agent primitives, and a small catalog promoted only from repeated evidence. Within one attempt, a registered LangGraph graph owns bounded research, synthesis, and revision. Exploratory multi-agent composition must remain bounded; it is not the durable process ledger.
- **the control-plane runtime — control plane, not another runtime.** Dynamically assembles bounded, objective-specific teams through Agent surfaces, invokes brick capabilities through MCP, and renders evidence. It does not own a parallel agent runtime or static domain team.
- **Capability bricks — deterministic execution.** Execute typed, bounded operations through MCP and guarantee their declared contracts. They do not adaptively plan, revise objectives, or own cross-brick lifecycle.
- **Workflow brick — durable attempts.** Owns cross-brick attempt history, global budgets, retries, cancellation, recovery, stopping rules, and terminal reasons. It remembers what ran; it does not perform intelligent research or synthesis.
- **Dataset brick — immutable materialization.** Validates and materializes immutable blueprints through allowlisted references. Its only retries are bounded, idempotent internal replays over frozen inputs or checkpoints; Workflow owns global retries, and Agent Graph owns deficiency-driven revision.
- **Games brick — reward and evidence.** Emits reward signals and supporting evidence for strategic outcomes. It does not accept or promote artifacts, trajectories, datasets, or models.
- **Evals brick — independent challenge.** Owns frozen evaluation policies, immutable evidence-bound reports, typed deficiencies, acceptance, and promotion. Agents may propose work but cannot supply executable validators or change criteria after results are observed.

**Domain-neutral acceptance gate.** Prove every generic control-plane path with two unrelated domains using the identical Agent → Workflow → capability bricks → Evals runtime path. Registered specialized computational adapters are allowed when selected through typed, immutable references; domain-specific orchestration branches are not.

## RULES

PLATFORM DOCTRINE — the control-plane runtime is a domain-agnostic expert-augmentation engine wrapped by a single interaction surface: the control-plane runtime Web (Next.js). Depth is a mode of that cockpit (embedded Monaco + the existing agent + the `sandbox` brick), added when a task warrants it — there is one cockpit until a second surface earns its place. The engine is built once; a domain is pure data (persona/skills/SOP + taxonomy + game config + presentation manifest + eventually a LoRA adapter). Zero `if domain == ...` anywhere; security is domain pack #1. Tools are three layers: expertise→agents, capabilities/connectors→MCP (the connector marketplace), visualization→render surfaces. Details: `.agents/steering/platform-doctrine.md`

ARCHITECTURE — Polymorphic, clean, agnostic. <200 LOC per file. SRP. Business logic in `runtime/`, MCP in `mcp/`, public API in `interface.py`. Bases are pure transport shells. No cross-imports (use `factory.<brick>.interface`). Details: `.agents/steering/dev-principles.md`

SDK-FIRST — Favor framework primitives over bespoke wrappers. **Runtime truth (2026-10-02): the agent chat/graph runtime is Strands Agents SDK 1.56 over MCP v2 (streamable HTTP) — the LangGraph→Strands route flip (GH #89) is complete on main. The LangChain 1.x + LangGraph 1.x adapter is DORMANT, not deleted: still registered and selectable via `AGENT_RUNTIME_ADAPTER=langchain`, with its deps isolated in the `langgraph-legacy` dependency-group (import-lazy everywhere; group-less test collection skips, not fails). Deletion criterion: only after ~1 quarter clean Strands production AND no persona/project needs LangGraph-native features — re-evaluate at the migration retrospective; until then do not delete the dormant adapter or cite LangChain as the baseline. Strands ships `Agent`, hook providers (BeforeToolCallEvent interrupts → interruptResponse replay; BeforeModelCallEvent steer injection), pluggable `SessionManager`/`SessionRepository` over the storage brick's `SQLStore` port (backend-swappable to Postgres/Aurora), `strands.multiagent` for graphs/swarms, and `strands.tools.mcp.MCPClient` for MCP v2 tool loading. Chat models are built from `llm_gateway.resolve_chat_profile()` profiles; secrets are referenced by env-var *name*, never value. The strands-evals canary in `components/evals` is now the primary evals adapter.

BRICKS — Every brick follows the same structure: BRICK.yaml, `runtime/ports.py` (Protocol), `mcp/` primitives, `interface.py`. Workflow brick is the exemplar. Details: `.agents/steering/brick-anatomy.md`

SCAFFOLDING — Use foreman MCP tools for all brick creation, compliance checks, and index management. `foreman_guardian_check` is the gate. Details: `.agents/steering/workflow.md`

TESTING — Hypothesis property tests required for all stateful bricks. Recipes in `.agents/recipes/` define E2E scenarios. Run existing tests before writing new ones. Details: `.agents/steering/hypothesis-testing.md`

MEMORY — Use the control-plane runtime memory brick (NOT a-mem). `memory_store`, `memory_retrieve` via `call_brick_tool`. Omit `user_id`; the brick scopes to the authenticated principal. Details: `.agents/steering/companion-memory.md`

ISSUE TRACKING — Beads (`bd`) is the single source of truth. `bd ready --json` | `bd update <id> --claim` | `bd close <id> --reason "..."` | `bd create "title" -p <0-4> --deps discovered-from:<id>`. No markdown TODOs. Details: `.agents/steering/beads-workflow.md`

SHELL SAFETY — Always use non-interactive flags: `cp -f`, `mv -f`, `rm -f`, `rm -rf`. Never let shell commands hang on prompts.

MODELS — Chat models are built from a safe `llm_gateway.resolve_chat_profile()` profile by the **Strands factory `components/agent/.../runtime/adapters/strands_model.py` (default runtime)**; the dormant LangChain factory `langchain_model.py` builds the same profiles for the langgraph-legacy route: `openrouter/<vendor>/<model>` (or `COMPANION_X_CHAT_MODEL=openrouter` + `OPENROUTER_MODEL`) → `ChatOpenAI`; `ollama/<model>` → `ChatOllama`; bare Bedrock id → `ChatBedrockConverse`. Secrets are referenced by env-var *name* in profiles, never by value. The historical Strands Mantle adapter (`strands_mantle_model.py`) is deleted; `.agents/steering/gpt5-mantle-models.md` is historical. Any OpenAI-compatible endpoint (opencode, LM Studio, vLLM) is supported via `openai-compat/<name>` profiles. Where the provider rejects a request without an affinity header (opencode-go `400 MissingSessionID`), set the per-profile name knob `<STEM>_SESSION_HEADER` (name only, e.g. `OPENCODE_SESSION_HEADER=x-opencode-session`); the gateway derives the value per conversation (`ses_`+sha256(thread_id)[:32], stable across restarts, never a secret, never configured) and every profile→client builder — strands, plus the LangChain title/summary/memory/side-chat paths — now sends it. Remote `_BASE_URL` origins must still be allowlisted in `COMPANION_X_OPENAI_COMPAT_REMOTE_ORIGINS`.

UI — Views are data, not code. Bricks declare views in `mcp/views.py`. A2UI is a payload schema, AG-UI is the wire. The chat surface uses four carriers — see `.agents/steering/a2ui-protocol.md` for the canonical model. The active frontend is the control-plane runtime (Next.js + shadcn/ui + recharts). HTMX/DaisyUI and Flet dashboards are legacy adapters — do NOT reference them as the current UI. Details: `.agents/steering/a2ui-protocol.md`

LOCAL COMPANION-X DEV — For the lightweight local stack, source `projects/the control-plane project/.env`, then start the API with `uv run python -m factory.api.main`. The editable install puts every brick's `src/` on the Python path automatically via Hatchling's `[tool.hatch.build] dev-mode-dirs` declaration in `pyproject.toml` — no `PYTHONPATH` overrides needed for `uv run`, ad-hoc `python -m`, Kiro powers, or the API process (bd:python-factory-9wcd). The Next dashboard should point at `API_URL=http://127.0.0.1:8000` via `frontends/next-dashboard/.env.local` and be restarted after env changes. Chat uses `COMPANION_X_CHAT_MODEL` (see MODELS); `ollama/<model>` needs the Python `ollama`/`langchain-ollama` packages installed, otherwise the LangChain model factory falls through to the Bedrock path and fails with credential/profile errors even when Ollama itself is running. Optionally set `COMPANION_X_CHAT_THINKING_BUDGET=16000` to enable Claude extended thinking on Sonnet 4.6 (Haiku/Nova/Llama no-op); the v2 chat sidebar auto-renders the Thinking panel via REASONING_MESSAGE_* events (bd:python-factory-tpfk). Local durable document/telemetry storage now uses `STORAGE_DOC_BACKEND=sqlite`, which resolves to `SQLiteDocumentStore` at `./.storage/docs.db`. Old TinyDB `JSONDecodeError` output usually means a stale process or shell is still running with the pre-switch env.

MCP PATTERNS — Tool categories: `@deterministic` (pure), `@operational` (stateful), `@authoring` (gated). Prefix with brick name. Details: `.agents/steering/mcp-tools.md`

MCP TOOL SCOPING — `MCP_INCLUDE_BRICKS=<comma-separated brick names>` on any process running `factory.mcp_server` (base or a project's own `server.py` calling `get_flat_view`) restricts the served tool surface to EXACTLY those bricks — nothing more. Total tools served = sum of the named bricks' tools, always. There is no bloat you're stuck with: composing N bricks in a project's `pyproject.toml` and setting `MCP_INCLUDE_BRICKS` to those same N brick names gives you only their tools. The "600+ tools" the control-plane runtime is sometimes cited with is what you get ONLY if you set `MCP_INCLUDE_BRICKS` to the control-plane runtime's own ~20-brick list (see `.kiro/specs/standalone-brick-servers/design.md`) — it is not a property of the `agent`/`mcp_server` bricks themselves, and no other project inherits it by composing those bricks. `MCP_DISCOVERY_MODE=progressive` (default) additionally exposes only 9 meta-tools until a brick is force-loaded via `get_brick_tools`; `flat` mounts everything in `MCP_INCLUDE_BRICKS` immediately. Same scoping applies in-process to the LangChain agent's tool wiring via `AgentConfig.tools` / `exact_tools=True` — pass an explicit allowlist and the agent sees only those tools, never the whole registry. Unscoped (`allowlist=None`) is the chat-persona default, not a brick limitation.

INVENTORY — Component and base counts are generated from `BRICKS_INDEX.yaml` (including `oracle`, the domain-agnostic verification oracle, bd:python-factory-216ti). Full catalog with adapter matrix. Details: `.agents/steering/brick-inventory.md`

ARCHITECTURE DEEP DIVE — Gateway pattern, progressive discovery (9 meta-tools), envelope context, CDK generation, the control-plane runtime. Details: `.agents/steering/project-overview.md`

PROGRESSIVE DISCOVERY — Project-level MCP servers (e.g. the control-plane runtime) use lazy loading. `list_bricks` only shows already-loaded bricks; `tools_count: -1` means the brick is registered but not yet loaded. Call `get_brick_tools(brick_name)` to trigger loading.

## SESSION PROTOCOL

1. Check `bd ready` for available work
2. Claim before starting: `bd update <id> --claim`
3. When done: `bd close <id> --reason "..."`
4. Discovered new work? `bd create "title" --deps discovered-from:<parent-id>`
5. Before finishing: `foreman_guardian_check` if code changed
6. Push: `git pull --rebase && bd sync && git push`
7. Issue tracking: GitHub Issues (bannff/python-factory) superseded `bd` as of 2026-09-29 (bd local Dolt store unreparable: missing issue identity; `bd create` blocked). Use `gh` issue/label conventions (type/priority/status/brick labels).
